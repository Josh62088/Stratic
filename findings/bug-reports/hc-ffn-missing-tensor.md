# Engine exits on first token: blk.0.hc_ffn_up.weight is missing

## Summary

The engine loads fully, reports "session is up (engine 0.1.42)", then on the **first generated token**
fails with:

    strata serve: blk.0.hc_ffn_up.weight is missing
    400 invalid request: blk.0.hc_ffn_up.weight is missing
    the engine stopped unexpectedly (exit code 1)

A second request reports `blk.0.hc_ffn_down.weight is missing`.

## Version

    checkout      : v0.1.42-6-g36fe6e9  (6 commits past the v0.1.42 tag)
    engine        : 0.1.42, built 2026-10-11 18:50
    model         : IQ2_XS, Qwen3.8-Flash-Next-GSQ-RCO-IQ2_XS-00001/00002-of-00002.gguf
    pack          : v3, generated by tools/iq_pack.py
    hardware      : RTX 5060 Ti 16 GB (sm_120), Ryzen 5 5500, 32 GB RAM, Ubuntu 24.04
    mode          : --mmap-experts (low-RAM), --max-context 32768, --kv int8

## What is present and what is not

The pack index (`packs/iq2_xs/index.txt`, 985 lines) lists per block:

    blk.N.hc_ffn_inject.weight    present (48 entries)
    blk.N.hc_ffn_norm.weight      present (48 entries)
    blk.N.hc_ffn_up.weight        ABSENT  (0 entries)   <-- engine asks for this
    blk.N.hc_ffn_down.weight      ABSENT  (0 entries)   <-- engine asks for this

The source GGUF **does** contain all four (verified: `blk.0.hc_ffn_up.weight`,
`blk.0.hc_ffn_down.weight`, `blk.0.hc_ffn_inject.weight`, `blk.0.hc_ffn_norm.weight` all appear in the
model shard), and the engine binary **does** look for all four (all four name fragments are in `strings`).

So the tensors exist in the model, the engine wants them, and the packer drops them.

## Why this looks like a packer bug rather than a model problem

It is **selective**: `output_hc_up.weight` and `output_hc_down.weight` ARE in the index, so
`tools/iq_pack.py` handles some `_up`/`_down` hyper-connection tensors and silently omits others --
specifically the per-block FFN pair.

Possibly related: `conversions.json` has `"tensors": []` (empty), so the packer recorded no conversions.

The six commits after the v0.1.42 tag touch `gguf_reader`, `geometry_map`, `generate.cpp` and
`tools/iq_pack.py` -- the load path and the packer were both being changed, so an engine built at that
point may not agree with a pack generated from it.

## Reproduce

    ./setup.sh --setup --model IQ2_XS --family qwen --context 32768 --vision no --yes --no-start
    ./run-iq2_xs.sh
    curl -s localhost:8080/v1/chat/completions -H 'Content-Type: application/json' \
      -d '{"model":"qwen3.8-flash-next-iq2_xs","messages":[{"role":"user","content":"hi"}],"max_tokens":16}'

## Note

`setup.py` could not install a prebuilt engine for v0.1.42 (`releases/latest/download` returns 404), so it
fell back to compiling, which needs the CUDA 13 toolkit via `apt`/`sudo`. The engine used here is a
locally built sm_120 engine from the same checkout.
