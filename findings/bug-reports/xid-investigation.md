# Strata 0.1.42 on sm_120: two bugs, one with a kernel-level root cause

Two separate defects found running the Qwen3.8-Flash-Next IQ2_XS build on a 3× RTX 5060 Ti / 32 GB
Ryzen 5 5500 box. They are reported together because they were hit in the same session and the second
one is what makes the engine unusable in low-RAM mode.

- **Bug 1 — packer misclassifies hyper-connection FFN tensors.** Engine asks for tensors the packer
  silently dropped. Reproducible, one-line cause, fixed and verified locally.
- **Bug 2 — GPU page fault in the graphics engine during dequant.** Identified from the kernel log
  (Xid 31, MMU fault), which is new information not previously available to this project.

---

# Bug 1 — `blk.0.hc_ffn_up.weight is missing`, engine exits on the first token

## Summary

The engine loads fully, reports `session is up (engine 0.1.42)`, then on the **first generated token**
fails with:

    strata serve: blk.0.hc_ffn_up.weight is missing
    400 invalid request: blk.0.hc_ffn_up.weight is missing
    the engine stopped unexpectedly (exit code 1)

A second request reports `blk.0.hc_ffn_down.weight is missing`.

## Version

    checkout      : v0.1.42-6-g36fe6e9  (6 commits past the v0.1.42 tag)
    engine        : 0.1.42, built 2026-10-11 18:50, sm_120
    model         : IQ2_XS, Qwen3.8-Flash-Next-GSQ-RCO-IQ2_XS-00001/00002-of-00002.gguf
    pack          : v3, generated by tools/iq_pack.py
    hardware      : RTX 5060 Ti 16 GB (sm_120), Ryzen 5 5500, 32 GB RAM, Ubuntu 24.04
    mode          : --mmap-experts (low-RAM), --max-context 32768, --kv int8

## Cause

`tools/iq_pack.py`'s `is_expert()` was widened in an unmerged local commit to:

```python
name.endswith(("_exps.weight", "ffn_gate.weight", "ffn_up.weight", "ffn_down.weight"))
```

`"blk.0.hc_ffn_up.weight".endswith("ffn_up.weight")` is **True**, so the hyper-connection FFN tensors
were classified as routed experts and never written to the pack.

The commit's own comment claims the change is safe because "those three names do not exist in the 125B".
They do exist — as `hc_ffn_up` / `hc_ffn_down`.

Verified directly against the tag and HEAD:

| tensor | v0.1.42 tag | HEAD |
|---|---|---|
| `blk.0.hc_ffn_up.weight` | False | **True** ← misclassified |
| `blk.0.hc_ffn_down.weight` | False | **True** |
| `blk.0.ffn_gate_exps.weight` | True | True ← real experts, correct |

The pack index confirms it: `hc_ffn_up` and `hc_ffn_down` had **0 entries**, while
`output_hc_up.weight` / `output_hc_down.weight` were present — so the packer handles some
hyper-connection tensors and silently omits the per-block FFN pair.

Possibly related: `conversions.json` has `"tensors": []`.

## Suggested fix

Require the dot-segment before `.weight` to be exactly the FFN role, rather than suffix-matching:

```python
role = name.rsplit(".", 2)[-2] if name.endswith(".weight") else ""
is_expert = role in {"ffn_gate_exps", "ffn_up_exps", "ffn_down_exps"}
```

With the predicate corrected and the pack regenerated:

    hc_ffn_up    0 -> 48 entries
    hc_ffn_down  0 -> 48 entries
    index        983 -> 1079 tensors

The engine then generates tokens.

## Reproduce

    ./setup.sh --setup --model IQ2_XS --family qwen --context 32768 --vision no --yes --no-start
    ./run-iq2_xs.sh
    curl -s localhost:8080/v1/chat/completions -H 'Content-Type: application/json' \
      -d '{"model":"qwen3.8-flash-next-iq2_xs","messages":[{"role":"user","content":"hi"}],"max_tokens":16}'

# Bug 2 — `dequant launch: an illegal memory access`, with an Xid 31 MMU fault in the kernel log

## Summary

After a handful of requests in low-RAM mode:

    dequant launch: an illegal memory access was encountered
    the engine stopped unexpectedly (exit code 1)

The server restarts the engine on the next request, but it keeps recurring. **The kernel log identifies
the mechanism**, which the engine's own error message does not:

    NVRM: Xid (PCI:0000:01:00): 31, pid=125865, name=strata, channel 0x00000003, intr 00000000.
          MMU Fault: ENGINE GRAPHICS GPC2 GPCCLIENT_T1_11 faulted @ 0x9841_de9d4000.
          Fault is of type FAULT_PDE ACCESS_TYPE_VIRT_READ
    NVRM: Xid (PCI:0000:01:00): 31, pid=138294, name=strata, channel 0x00000002, intr 00000000.
          MMU Fault: ENGINE GRAPHICS GPC0 GPCCLIENT_T1_0 faulted @ 0x7e1b_6d51c000.
          Fault is of type FAULT_PDE ACCESS_TYPE_VIRT_READ
    NVRM: Xid (PCI:0000:01:00): 31, pid=145311, name=strata, channel 0x00000002, intr 00000000.
          MMU Fault: ENGINE GRAPHICS GPC2 GPCCLIENT_T1_3 faulted @ 0x962b_c82d0000.
          Fault is of type FAULT_PDE ACCESS_TYPE_VIRT_READ

## Why this is more specific than "illegal memory access"

Three things in that trace matter:

1. **Xid 31 is an MMU fault**, and the fault type is `FAULT_PDE ACCESS_TYPE_VIRT_READ` — a **page
   directory entry** fault on a virtual *read*. The address was not merely out of bounds; its page
   mapping did not exist at all.
2. **`ENGINE GRAPHICS`, not a compute engine.** A CUDA kernel launched normally would fault on a compute
   channel. The fault is attributed to the graphics engine, which suggests work is being dispatched
   through the graphics path — a real distinction, and one that points at how the dequant launch is
   issued rather than at the arithmetic it performs.
3. **`GPC2` / `GPC0` / `GPC2` with different `GPCCLIENT_T1_*` clients across three runs.** The fault
   moves around the chip between attempts, which is consistent with a mapping that is established
   late, reused, or freed while still resident — not with a single fixed bad offset.

## Correlating evidence from the same session

    decode expert cache hit rate: 70-86%
    expert tiers: RAM 0 blobs, files 0 blobs, 33,641 MB read (the GGUF in place)
    file tier I/O: the OS read 19,088 MB from storage (15,937 major faults)

This is the low-RAM path behaving as documented, so the fault appears to be in that path. The engine
holds `--mmap-experts` mappings and faults while reading them.

## Suggested next step for maintainers

The Xid 31 in `ENGINE GRAPHICS` during `dequant` is the concrete lead. If the dequant kernel is launched
on the graphics queue, or if a mapped region is unmapped while the dequant still holds a pointer into
it, that would produce exactly this signature. Worth checking whether the dequant path can be moved to a
compute queue, and whether the mmap'd expert regions are pinned for the lifetime of the launch.

## Environment note (not a bug)

`setup.py` could not install a prebuilt engine for v0.1.42 — `releases/latest/download` returns 404 — so
it fell back to compiling, which requires the CUDA 13 toolkit via `apt`/`sudo`, and this box has no sudo
password available to the session. Worked around by installing an existing local `sm_120` build and
writing a `BUILD.json` (`version 0.1.42`, `archs [120]`, `cuda 12`, `lib_dirs` pointing at the CUDA 12
wheels already on disk, which matches the driver's `runtime 12080`). `get_prebuilt()` then accepts it.
Worth noting only because a 404 on the documented install path sends users into a compile they may not
be able to complete.

## How to reproduce and collect the log

    sudo dmesg -w | grep -i nvrm        # or: journalctl -k -f -g NVRM
    # then drive a few requests through the engine until "dequant launch" appears

The Xid lines appear in the kernel log, not in the engine's output, so the engine's own report is less
informative than what the driver records.
